## Преамбула
В компании используется мессенджер MatterMost, в нем есть возможность создавать интеграции через вебхуки и ботов. Но нет возможности узнавать сколько запросов они создают и как нагружают сервис. Хочется реализовать заготовку для плагина, который будет учитывать все запросы и настраивать для каждого вида запросов свои лимиты.

Как это устроено:
- Вебхуки - это запросы, которые начинаются с префикса /hook/{random_string}, где random_string - это сгенерированная строка из случайных символов.
- боты - для ботов генерируется токен, их может быть несколько, и указываю этот токен в заголовке авторизации, как Bearer Token, проходит авторизация в сервисе и разрешается делать различные дейтствия.

## Общее описание
Сервис предназначен для учета и блокировки запросов в какой-либо системе (позже адаптируется под плагин для MatterMost)

Сервис вызывается перед выполнением запросов и может либо разрешить, либо заблокировать запрос.

Предполагается, что сервис используется только для server-server, т.е. скрыт от конечного пользователя.

## Алгоритм работы
Сервис учитывает и ограничивает частоту запросов, например:
* не более A = 10 попыток в минуту для одного бота
* не более B = 10 попыток в час для одного токена.
* не более C = 100 попыток в минуту для данного хука.

Для подсчета и ограничения частоты запросов, можно использовать например алгоритм leaky bucket.
Или иные аналогичные: https://en.wikipedia.org/wiki/Rate_limiting

Причем сервис будет поддерживать множество bucket-ов, по одному на каждый токен/бот/хук.

Bucket-ы можно хранить:
* в памяти (в таком случае нужно продумать удаление неактивных bucket-ов, чтобы избежать утечек памяти).
* во внешнем хранилище (например redis или СУБД, в таком случае нужно продумать производительность).

Также сервис предоставляет метрики в формате Prometheus с количеством запросов каждого типа запроса, а также с количетвом блокировок запросов каждого типа.


## Архитектура
Микросервис состоит из API, базы данных для хранения настроек.
Опционально - хранилище для bucket'ов. Сервис должен предоставлять GRPC **или** REST API.

## Описание методов API

### Создание сообщения
Запрос:
* text
* data
* ip

Заголовок:
* Authorization: Bearer

Ответ:
* 200 код ответа, и  ok (true/false) - сервис должен возвращать ok=true, если считает что запрос нормальный
  и ok=false, если превысили лимит запросов.
* 401 код ответа - если токен не найден в базе

### Хуки
Запрос:
* text

Ответ:
* ok (true/false) - сервис должен возвращать ok=true, если считает что запрос нормальный
  и ok=false, если превысили лимит запросов.

### Отображение всех сущностей
Должен вывести 2 массива: список хуков и список ботов с их токенами

### Метрики
Отоборажает метрики в формате прометеус, сколько запросов сделано в разрезе каждого хука/бота/токена и сколько заопросов заблокировано.

### Сброс метрик хуков, токена или бота
Должен очистить bucket-ы соответствующие переданным login и ip.
* type - одно знаечние из трех [hook, token, bot]
* id

### Добавление хука
* название

### Удаление хука
* id

### Добавление бота
* название бота

### Удаление бота
* id

### Добавление токена
* название
* id бота

### Удаление токена
* id токена

## Конфигурация
Основные параметры конфигурации: A, B, C - лимиты по достижению которых, сервис считает попытку брутфорсом.

## Command-Line интерфейс
Необходимо так же разработать command-line интерфейс для ручного администрирования сервиса.
Через CLI должна быть возможность вызвать сброс бакета и управлять ботами и хуками.
CLI может работать через GRPC/HTTP интерфейс.

## Развертывание
Развертывание микросервиса должно осуществляться командой `make run` (внутри `docker compose up`)
в директории с проектом.

## Тестирование
Рекомендуется выделить модуль обработки одного bucket и протестировать его с помощью unit-тестов.

Так же необходимо написать интеграционные тесты, проверяющие все вызовы API.
